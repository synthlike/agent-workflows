# v0.3 project-foundation and feedback workflows

## Problem

Agent Workflows helps users clarify intent, research facts, model domains, make decisions, specify behavior, and plan implementation. It does not yet guide two recurring parts of project work: establishing sound engineering conventions when a technical stack is already fixed, and turning implementation evidence into diagnosis, regression protection, conformance findings, and honest initiative outcomes.

Without explicit workflows, agents can offer generic “best practices,” invent product architecture before product intent is known, silently fix work while reviewing it, create premature issues, or infer completion from issue status rather than evidence.

## Desired behavior

A user adopting v0.3 can establish a minimal, production-compatible technical baseline at a project-approved documentation location. During delivery, the user can triage incoming work, diagnose a failure without conflating diagnosis with repair, capture a confirmed defect as a durable regression check, review actual implementation against authoritative intent, and close an initiative with an evidence-based outcome.

Each operation preserves project ownership, uses existing artifact authority, makes approval boundaries explicit, and remains independent of application stack, issue backend, test framework, and agent harness. v0.3 retains schema 2 and reviewed manual updates.

## Requirements

### Common workflow contract

1. v0.3 MUST distribute skills named `establish-technical-baseline`, `triage-issue`, `investigate-failure`, `capture-regression`, `review-implementation`, and `close-initiative`.
2. Each skill MUST use lowercase verb-object naming, valid Agent Skills frontmatter, relative links, and intact self-contained references.
3. Each skill MUST describe when it applies, what context it inspects, what it proposes before writing, which user approvals it requires, what durable output it may create, and when it must stop.
4. Each skill MUST inspect repository facts and configured project guidance before asking for information already available.
5. Each skill MUST preserve existing project conventions and consumer-owned files unless a specific change is shown and approved.
6. Each skill MUST distinguish authoritative requirements and decisions from supporting evidence, recommendations, and agent interpretation according to the artifact model.
7. Each skill MUST use the configured issue backend for issue operations and MUST stop with configuration guidance when required backend instructions are unavailable.
8. Skills MUST route unresolved human decisions to clarification or RFC development, external factual questions to research, consequential accepted technical decisions to ARPs, agreed behavior to specifications, and executable work to issues.
9. Routing to another workflow MUST NOT silently perform that workflow's approval-sensitive writes in the same step.
10. No skill MAY assume a fixed repository path, skill parent directory, programming language, framework, cloud, database, test runner, issue tracker, or agent harness.
11. A failed or incomplete workflow MUST report verified progress, remaining uncertainty, and any repository changes; it MUST NOT claim the intended outcome.

### Establish a technical baseline

12. `establish-technical-baseline` MUST apply when principal technology choices are already constraints and the user wants engineering foundations before product-dependent design.
13. The workflow MUST collect the intended maturity level, fixed technologies and versions, deployment constraints, repository state, existing conventions, and known quality or regulatory constraints.
14. The default maturity target MUST be a minimal but production-compatible foundation: establish guardrails expensive to retrofit while deferring architecture that depends on product behavior, scale, tenancy, consistency, or domain boundaries not yet known.
15. The workflow MUST prefer official documentation, specifications, support policies, and first-party platform guidance for compatibility and operational claims.
16. The workflow MUST distinguish verified compatibility facts from context-dependent recommendations and generic agent knowledge.
17. The workflow MUST consider only applicable baseline areas, including repository structure, dependency boundaries, version policy, configuration and secrets, local development, testing layers, deployment, observability, security, data lifecycle, and operational ownership.
18. The workflow MUST NOT select a technology that the user has not approved or infer product and domain architecture from the selected stack.
19. The workflow MUST identify contradictions, unsupported versions, missing operational prerequisites, and choices that cannot remain safely deferred.
20. Routine reversible conventions MAY be proposed in the baseline. Consequential choices MUST be routed to an RFC and, after acceptance, an ARP rather than being presented as settled by the baseline.
21. Before writing, the workflow MUST show the proposed baseline sections, classifications, target location, related artifacts, and all other file changes.
22. The workflow MUST prefer an established engineering or architecture documentation location. If none exists, it MUST ask the user to approve a repository-contained location and MUST NOT hardcode a toolkit-wide baseline path.
23. The durable baseline MUST inventory fixed technologies and supported versions; classify facts, approved conventions, recommendations, open decisions, and deferred product questions; and link rather than duplicate ARPs, RFCs, specifications, and external evidence.
24. The baseline is a supporting index. It MUST NOT become authority for unresolved decisions or agreed product behavior.

### Triage an issue

25. `triage-issue` MUST apply to an incoming report, observation, defect claim, or requested change that is not yet actionable executable work.
26. The workflow MUST read the configured backend instructions and search open and resolved issues for duplicates, overlap, prior disposition, and related authoritative artifacts.
27. It MUST classify the input at least as a defect, enhancement, question, design ambiguity, operational task, or duplicate, while allowing project-specific classifications.
28. It MUST distinguish reported impact and urgency from verified severity and MUST not invent priority or business impact.
29. It MUST identify available evidence, missing facts, reproduction needs, decision needs, affected outcomes, and the smallest useful next routing step.
30. It MUST route uncertain runtime behavior to failure investigation, external facts to research, human intent to clarification, and material design ambiguity to an RFC before proposing implementation.
31. When an issue is appropriate, it MUST propose one bounded outcome, observable acceptance criteria, relevant links, and genuine blockers without speculative implementation detail.
32. Before creating or materially rewriting an issue, it MUST present its classification, duplicate analysis, evidence, missing information, proposed scope, acceptance criteria, and routing recommendation and receive approval.
33. After approval, it MUST perform issue operations through the configured backend and report the resulting stable issue reference.
34. A duplicate, unsupported report, or question MAY resolve without creating an issue, but the workflow MUST explain the disposition and preserve approved evidence in the appropriate existing artifact.

### Investigate a failure

35. `investigate-failure` MUST apply to unexpected observable behavior whose cause is not established.
36. The workflow MUST define expected behavior from an authoritative source or explicitly label it as an unconfirmed expectation.
37. It MUST record the observed behavior, relevant environment, reproducibility, scope, and exact reproduction command or procedure when one is available.
38. It MUST inspect current code, configuration, logs, tests, recent changes, and existing issues before proposing causes.
39. It MUST state competing hypotheses and test the cheapest discriminating evidence first rather than committing to the first plausible explanation.
40. Disposable probes MUST be narrowly scoped, disclosed, and removed before completion unless the user approves retaining them.
41. The workflow MUST avoid permanent production fixes and MUST not broaden investigation into opportunistic refactoring.
42. The outcome MUST identify a supported root cause or bound the remaining uncertainty, list evidence and falsified hypotheses, assess reproduction reliability, and recommend the smallest next action.
43. The workflow MUST ask before writing findings to an issue or creating follow-up work. It MUST not change issue status as an investigation side effect.
44. When the failure cannot be reproduced, the outcome MUST state what was attempted, which evidence is missing, and what observation would allow investigation to continue.

### Capture a regression

45. `capture-regression` MUST start from an accepted defect with a reliable reproduction or sufficiently established failure mechanism.
46. If the failure is not established, the workflow MUST stop and recommend investigation instead of encoding speculation as a test.
47. It MUST inspect existing test organization and select the narrowest test level that reproduces the user-visible or contract-visible defect without coupling unnecessarily to implementation details.
48. Before writing, it MUST show the proposed test seam, files, command, expected failing signal, and any fixture changes and receive approval.
49. The new check MUST fail before the production fix and the workflow MUST demonstrate that it fails for the diagnosed reason rather than an unrelated environment or setup error.
50. The workflow MUST avoid production behavior changes, unrelated cleanup, broad fixture growth, redundant assertions, and dependence on unstable external services when a stable seam exists.
51. It MUST follow project test conventions and minimize new data, time, network, and environment requirements.
52. Completion MUST report changed test files, the narrow verification command, observed failing result, and the defect or issue the check protects.
53. The workflow MUST NOT commit automatically. When project policy prohibits a red commit, the check MAY remain uncommitted or land atomically with a separately implemented fix.
54. When durable automation is impractical, the workflow MUST explain why and propose an explicit manual or higher-level verification alternative for approval.

### Review an implementation

55. `review-implementation` MUST apply to actual implementation associated with a bounded issue, specification, settled plan, commit range, or working-tree change.
56. It MUST establish the review scope and stop for clarification when the relevant change set or authoritative intent cannot be identified.
57. It MUST read the implementation issue and acceptance criteria, agreed specifications, accepted ARPs, relevant project guidance, and the actual code, configuration, tests, documentation, and repository diff or state.
58. Accepted ARPs constrain technical choices, specifications define agreed behavior, issues define the executable slice, and code and tests show current behavior. RFC discussion MAY explain context but MUST NOT override those authorities.
59. The workflow MUST verify behavior and important failure cases at the highest stable available seam and MUST not infer conformance solely from test presence or resolved issue status.
60. Findings MUST be limited to material correctness, safety, security, operability, compatibility, documented project conventions, scope, or verification gaps. Undocumented stylistic preference MUST NOT become a finding.
61. Each finding MUST include severity, authoritative expectation, concrete implementation evidence, impact, and recommended disposition.
62. The review MUST return exactly one verdict: `Conforms`, `Conforms with follow-up`, or `Does not conform`.
63. `Conforms` means no material discrepancy was found within the reviewed scope; it MUST NOT claim proof that no defect exists.
64. `Conforms with follow-up` requires the accepted behavior to be present and all findings to be non-blocking. `Does not conform` requires at least one material conflict with authoritative behavior, decision, acceptance criterion, or required failure handling.
65. Review MUST be read-only with respect to the implementation. It MUST NOT silently fix code, tests, configuration, or documentation.
66. The workflow MUST present the verdict and findings before writing review comments, changing issue state, or proposing follow-up issue creation. Those actions require user approval and configured backend operations.
67. An empty findings list MUST still state reviewed scope, authorities, evidence, and verification performed.

### Close an initiative

68. `close-initiative` MUST apply when work against a defined initiative destination is ending, whether through completion, partial delivery, or intentional abandonment.
69. It MUST identify the initiative map or equivalent parent, original destination, success criteria, accepted scope changes, linked implementation work, and authoritative specifications and decisions.
70. It MUST inspect delivered behavior and review or verification evidence rather than count resolved issues as proof of completion.
71. It MUST reconcile unresolved, blocked, cancelled, and deferred work and distinguish work that is no longer necessary from work that remains valuable.
72. The workflow MUST propose exactly one outcome: `Achieved`, `Partially achieved`, or `Abandoned`.
73. `Achieved` requires verified satisfaction of the destination and success criteria. `Partially achieved` requires useful verified outcomes plus explicit gaps. `Abandoned` requires rationale, delivered remnants, and consequences of stopping.
74. Before changing the initiative map, parent issue, or related issues, it MUST present the outcome, evidence, gaps, proposed dispositions, follow-up work, and exact artifact changes for approval.
75. After approval, it MUST update the existing initiative map or parent artifact with a concise closure summary and links. It MUST not create a separate canonical closure-report type.
76. Follow-up issues MUST be created only after approval, through the configured backend, and MUST not make partial delivery appear complete.
77. The closure summary MUST preserve useful lessons as evidence while routing lasting decisions, behavior, and terminology to ARPs, specifications, and domain documentation respectively.

### Distribution and adoption

78. Release metadata and the generated distribution manifest MUST identify `v0.3.0`, retain configuration schema 2 compatibility, and inventory every distributed skill and file.
79. The dependency table MUST publish every new skill's exact direct workflow dependencies, and calculated closure MUST include mandatory `configure-project` without assuming one physical parent directory.
80. The source repository's schema-2 installation inventory MUST include the newly selected skills at their actual discovered paths.
81. Fresh configuration MUST be able to select any new skill, calculate its closure, install missing dependencies from the verified v0.3 bundle, receive harness discovery confirmation, and verify from installed assets.
82. Existing v0.2 consumers MUST use the reviewed manual update procedure. Fresh-install planning and apply MUST NOT be presented as update commands.
83. README, workflow guidance, dependency documentation, customization guidance, changelog, and release notes MUST describe the new operations and the continued update boundary without duplicating skill contracts.
84. v0.3 MUST NOT introduce reusable update planning, replacement, transaction journals, backups, rollback, interruption recovery, lifecycle self-update, public migration tooling, or configuration schema 3.

## Constraints and decisions

- [RFC-0004](../rfcs/RFC-0004-focus-v0.3-on-project-feedback-workflows.md) accepts the six-skill scope and provisional v0.4 deferral of update automation.
- [ARP-0005](../decisions/ARP-0005-focus-v0.3-on-project-feedback-workflows.md) records the consequential roadmap boundary.
- The [artifact model](../artifact-model.md) remains authoritative for where facts, decisions, agreed behavior, executable work, and current behavior live.
- The [vendored consumer-owned boundary](../decisions/ARP-0001-use-a-vendored-consumer-owned-installation-boundary.md) and [configure-project bootstrap](../decisions/ARP-0002-use-configure-project-as-the-lifecycle-bootstrap.md) remain accepted.
- Schema 2 selected intent and exact discovered-path inventory remain unchanged.
- The technical baseline is supporting guidance and an index, not a new authority class.
- Transaction-safe updates may be reprioritized before v0.4 only when adoption or demonstrated update pain warrants a new decision.

## Verification

- **Skill structure:** Verify all six skill directories, frontmatter names and descriptions, relative links, references, and absence of consumer-specific paths or technology assumptions through the structural verifier.
- **Contract coverage:** Verify each skill contains its required trigger, inspection, proposal, approval, write, output, and stop behavior at the distributed `SKILL.md` and reference-file seam.
- **Authority and safety scenarios:** Exercise fixture scenarios for absent configuration, existing project conventions, unresolved intent, denied approval, incomplete evidence, and consumer-owned files; verify no unauthorized artifact or implementation mutation is instructed.
- **Technical baseline:** Exercise an empty project and a project with existing architecture guidance; verify location approval, primary-source distinction, minimal production-compatible scope, and routing of product-dependent decisions.
- **Triage:** Exercise a duplicate, unverified defect, design ambiguity, and actionable change; verify approval precedes backend writes and routing is appropriate.
- **Failure investigation:** Exercise reproduced, disproved, and non-reproducible failures; verify competing hypotheses, probe cleanup, bounded conclusions, and no permanent fix.
- **Regression capture:** Exercise a diagnosed defect, an unconfirmed report, project test conventions, and a failing-test policy; verify the check fails for the right reason and production files remain unchanged.
- **Implementation review:** Exercise conforming, follow-up, and non-conforming changes; verify authority ordering, concrete findings, exact verdicts, read-only behavior, and approval before issue operations.
- **Initiative closure:** Exercise achieved, partial, and abandoned outcomes; verify evidence rather than status counting, explicit gaps, approved follow-ups, and no separate authority type.
- **Dependencies:** Verify published direct dependencies and closure for each new selectable skill.
- **Distribution:** Regenerate and verify the v0.3 manifest and deterministic bundle; detect missing, extra, and modified distributed files.
- **Installed adoption:** Run a real installer and harness smoke test from an intentionally incomplete selection containing at least one new skill; confirm closure, schema-2 inventory, discovery, and source-checkout-free verification.
- **Regression:** Run all existing structural, unit, fixture, release, installed-consumer, script-syntax, and documentation-link checks.

## Out of scope

- Choosing a consumer's application stack.
- Product discovery, domain architecture, or product-dependent nonfunctional requirements without stakeholder input.
- General code implementation, automatic fixes, or opportunistic refactoring within the new review and investigation workflows.
- A new issue backend, artifact authority type, fixed technical-baseline directory, or configuration schema.
- Automated cross-version update, rollback, recovery, migration, conflict merging, or self-update.
- A broad cross-harness compatibility matrix.
