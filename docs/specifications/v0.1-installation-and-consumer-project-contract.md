# v0.1 installation and consumer-project contract

## Problem

A maintainer can currently copy some Agent Workflows skills into a repository and follow several setup documents, but there is no single testable contract that says when installation is complete, which files the toolkit may manage, or what an update must preserve. Consumers need reproducible installations that do not silently omit invoked workflows or overwrite project-owned configuration and artifacts.

## Desired behavior

A consumer can vendor a selected v0.1 workflow set through any compatible installer or by manual copying. The installation is valid when the selected set is dependency-closed, every skill is intact and discoverable, and `configure-project` has established one approved root configuration containing immutable distribution identity.

The consumer can review installation and update diffs with a clear ownership boundary: reusable vendored skill files may be updated, while project configuration, guidance, backend state, local changes, and artifacts remain under consumer control.

## Requirements

1. A v0.1 release MUST publish the [direct workflow dependency table](../workflow-dependencies.md).
2. An installer or operator MUST install `configure-project`, every explicitly selected skill, and the transitive closure of its listed dependencies.
3. The absence of optional supporting skills that are not in the selected closure MUST NOT invalidate an installation.
4. Every installed skill directory MUST retain its distributed name, `SKILL.md`, and all files reachable through relative references from that skill.
5. The consumer's agent MUST be able to discover every installed skill. The contract MUST NOT require a particular parent directory.
6. A manual copy and an installer-mediated copy MUST be treated equivalently when they produce the same files and discovery behavior.
7. Third-party installer commands MUST be labeled as examples rather than guaranteed interfaces.
8. Before another installed workflow is used, the operator MUST invoke `configure-project` from the Git repository root and explicitly approve its complete dry run.
9. A configured consumer MUST contain exactly one `.agents/workflows.yaml`, at the Git repository root.
10. Configuration inheritance and nested consumer roots within one Git repository MUST NOT be assumed or applied.
11. Every path in `.agents/workflows.yaml` MUST be repository-relative and resolve within the consumer root.
12. `.agents/workflows.yaml` MUST identify the distribution with `distribution.source` and `distribution.version`.
13. `distribution.version` MUST contain an exact release identifier or, for a local or prerelease installation, an immutable commit SHA. Mutable values such as `latest`, a branch name, or `unreleased` MUST NOT identify a completed installation.
14. `configure-project` MUST prefer existing project conventions, MUST NOT migrate existing artifacts, and MUST write only after approval.
15. Configuration MUST define the issue backend and configured artifact capabilities and paths needed by installed workflows.
16. After configuration, workflows MUST use `.agents/workflows.yaml` for consumer paths and capabilities and `docs/agents/issue-tracker.md` for issue operations.
17. Configuration MUST produce concise agent guidance that points to canonical workflow and backend guidance rather than duplicating it.
18. Disabled capabilities MUST remain disabled until a user explicitly approves enabling them.
19. Optional artifact and local issue directories MUST be created only when their first content is written.
20. The following are distribution-managed files: installed skill directories and their unmodified internal contents.
21. The following are consumer-owned files: `.agents/workflows.yaml`; root agent guidance; `docs/agents/`; backend state; project artifacts; and explicit local modifications to installed skills.
22. Installation MUST NOT overwrite existing consumer-owned files without the approved `configure-project` write step.
23. v0.1 updates MUST be performed as reviewable diffs and MUST NOT claim automatic merge or migration behavior.
24. An update MAY replace unmodified distribution-managed files.
25. An update MUST preserve consumer-owned files and MUST visibly surface a conflict before replacing a locally modified vendored file.
26. An update MUST NOT automatically migrate configuration schemas, backend state, or project artifacts.
27. `distribution.source` or `distribution.version` MUST be changed only when the corresponding installed source has been accepted.
28. A configured installation and every update MUST pass the release's consumer structural verification.
29. Consumer configuration and generated guidance SHOULD be committed before creating workflow artifacts.

## Constraints and decisions

- [ARP-0001](../decisions/ARP-0001-use-a-vendored-consumer-owned-installation-boundary.md) establishes the behavior-based vendored model and ownership boundary.
- One Git repository root is one consumer root in v0.1. Monorepos may customize paths inside that one configuration.
- Installed skills are repository-vendored, not globally shared mutable runtime state.
- Agent harnesses and installers may choose their own discoverable skill parent directories.
- Project policy overrides toolkit defaults; configuration and project guidance are preferred customization seams.
- v0.1 provides no automatic updater, rollback, conflict merge, schema migration, artifact migration, or custom dependency resolver.

## Verification

Verification MUST operate at stable consumer-visible seams rather than requiring a particular installer implementation.

- **Release dependency check:** Parse the distributed skills and fail when an explicit cross-skill invocation is absent from the published direct dependency table, or a table entry names a missing skill.
- **Selection closure check:** Given a selected skill list and the v0.1 table, fail when `configure-project` or any transitive dependency is absent.
- **Skill integrity check:** For each installed skill, verify its directory name and frontmatter name agree and every relative reference from `SKILL.md` resolves within the installed skill directory.
- **Discovery check:** Through the consumer agent's supported discovery interface, verify every installed skill can be addressed by its distributed name. This check is harness-specific but its outcome is required.
- **Configuration location check:** From any nested working directory in the repository, resolve exactly one configuration at the root; fail for a missing root configuration or an active nested configuration.
- **Configuration schema check:** Validate schema version, issue backend, enabled artifact settings, repository-contained relative paths, immutable distribution identity, and required guidance files.
- **Fresh-project setup scenario:** On an empty Git fixture, capture the dry run, approve it, verify only listed files are written, and verify optional artifact directories remain absent.
- **Existing-project setup scenario:** On a fixture with existing agent guidance and artifact conventions, verify the dry run adopts conventions, preserves surrounding guidance, and performs no migration.
- **Disabled-capability scenario:** Attempt to use a disabled optional capability and verify no artifact is written without explicit approval.
- **Update preservation scenario:** Modify consumer configuration, guidance, an artifact, and one vendored skill; apply an update and verify consumer-owned files remain unchanged while the local skill conflict is surfaced.
- **Mutable-version rejection:** Verify `latest`, branch names, and `unreleased` are rejected as the recorded identity of a completed installation.

## Out of scope

- Mandating `.agents/skills/` or any other physical skill parent directory.
- Guaranteeing a third-party installer's command syntax or behavior.
- Global installations shared by consumer repositories.
- More than one configured consumer root per Git repository.
- Automatic dependency resolution by a v0.1 installer.
- Automatic updates, rollback, local-change merging, or migrations.
- Migration or renaming of existing project artifacts during setup.
- Detailed semantics of individual artifacts or issue backend operations.
