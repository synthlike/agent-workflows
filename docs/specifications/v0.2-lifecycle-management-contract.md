# v0.2 lifecycle-management contract

> Superseded before implementation by [RFC-0003](../rfcs/RFC-0003-reduce-v0.2-to-fresh-project-lifecycle.md) and [ARP-0004](../decisions/ARP-0004-ship-v0.2-for-fresh-project-adoption.md). Current v0.2 behavior is defined by the [fresh-project lifecycle specification](v0.2-fresh-project-lifecycle.md); reusable updates are deferred to v0.3.

## Problem

A v0.1 consumer can install and operate Agent Workflows safely, but must manually calculate workflow dependency closure, use a distribution checkout for verification, and coordinate updates through documentation and an external copy mechanism. The consumer lacks one machine-readable release description and one deterministic operation that can verify, plan, apply, and recover an update while preserving consumer-owned files.

## Desired behavior

`configure-project` is the v0.2 lifecycle entrypoint. Its installed directory contains a deterministic lifecycle command and the current release manifest. The skill gathers intent, presents dry runs, requests explicit approvals, and explains conflicts. The command performs deterministic manifest, closure, integrity, plan, transaction, and recovery operations.

A fresh consumer can name selected workflows, obtain their closure from the current release bundle, review every destination, install missing skills, confirm harness discovery, and commit schema-2 configuration. A v0.1.0 consumer can run the standalone v0.2 command, verify its existing installation against a legacy baseline, separately approve schema migration, and enter the same lifecycle.

An established consumer can verify itself without a source checkout, stage a self-contained release bundle from a local path or HTTPS URL, review an immutable update plan, and apply exactly that plan. Failures restore the previous complete installation; interrupted work is recovered before another lifecycle operation. Configuration, guidance, backend state, artifacts, and local skill changes are never silently overwritten.

## Requirements

### Lifecycle entrypoint and command

1. Every valid v0.2 installation MUST include an intact `configure-project` skill.
2. `configure-project` MUST be the human-facing entrypoint for initial configuration, verification, update planning, update approval, and recovery guidance.
3. The `configure-project` directory MUST contain the deterministic lifecycle command and current release manifest through paths resolvable relative to its `SKILL.md`.
4. The skill MUST use the command for manifest parsing, dependency closure, file integrity, bundle validation, plan generation, apply, and recovery rather than reproducing those operations in prose.
5. The command MUST support non-interactive deterministic operations so behavior can be tested independently of an agent harness.
6. Human approval MUST remain outside the deterministic command. The command MUST NOT treat invocation alone as approval unless apply is given the exact approved plan identity.

### Release manifest and bundle

7. Each v0.2 release MUST publish one machine-readable manifest schema and generate one manifest for that release.
8. The manifest MUST identify its own format version, distribution source and exact release version, current and readable consumer-configuration schema versions, and canonical release-bundle location when available.
9. The manifest MUST contain every distributed skill, its direct skill dependencies, and every distributed file inside its skill directory except the manifest itself.
10. Each listed file MUST be keyed by skill-relative path and include its SHA-256 digest.
11. The manifest MUST NOT include installer lock files, symlinks created outside skill directories, caches, OS metadata, consumer configuration or guidance, backend state, transaction state, or project artifacts.
12. Manifest generation MUST be deterministic and MUST fail for unknown skills, missing dependencies, unlisted distributed files, duplicate paths, escaping paths, or stale dependency declarations.
13. A release bundle MUST be one immutable archive containing the manifest, complete skill directories, lifecycle command through `configure-project`, and release changelog information.
14. The command MUST accept a release bundle from a local path or HTTPS URL without requiring a hosting-provider API or third-party installer.
15. The command MUST compute SHA-256 over the complete archive bytes and bind every generated plan to that digest.
16. Archive extraction MUST reject absolute paths, parent traversal, duplicate members, links, device files, and content not allowed by the bundle layout.
17. After safe extraction, the command MUST verify every manifest-listed file and reject missing, extra, or mismatched files before planning.
18. Cryptographic signing and trust infrastructure beyond local input or HTTPS transport are not required in v0.2.

### Configuration schema 2

19. v0.2 consumer configuration MUST use `schema_version: 2`.
20. In addition to the v0.1 distribution, issue-backend, and artifact settings, schema 2 MUST contain an installation inventory with:
    - the workflows explicitly selected by the consumer; and
    - a mapping from every installed skill name in the resulting closure to its harness-discovered, repository-relative directory.
21. Selected workflows and installed skill names MUST be unique and MUST exist in the installed release manifest.
22. Inventory paths MUST be unique, remain within the consumer root, name directories matching their skills, and resolve to an intact dependency-closed set.
23. The lifecycle command MUST derive transitive dependencies from selected workflows rather than treating incidental installed dependencies as user intent.
24. No second Agent Workflows lock file may become canonical lifecycle state. Installer-owned lock files remain evidence only.
25. Distribution identity and installation inventory MUST change only through an explicitly approved configuration or update plan.

### Fresh configuration

26. Initial installation MAY contain only `configure-project` and some user-selected skills.
27. During configuration, the consumer MUST identify the workflows it intends to select and provide the current release bundle by local path or HTTPS URL when missing files are needed.
28. The command MUST calculate the complete closure, compare it with discovered installed skills, and report missing, unexpected, modified, or duplicate skills.
29. For each missing skill, the command MUST propose a destination beside the discovered `configure-project` directory by default and MUST allow an explicit repository-contained destination override.
30. The dry run MUST show selected workflows, calculated closure, source bundle identity, every source and destination, file actions, configuration changes, and any existing-file conflict.
31. Applying the approved fresh-install plan MUST use the same integrity, precondition, journal, backup, and recovery rules as an update.
32. Configuration MUST NOT complete until the consumer's harness confirms discovery of every installed skill in the closure.
33. Optional artifact and issue directories MUST remain lazy after configuration.

### Verification

34. Consumer verification MUST run from installed lifecycle assets without a distribution source checkout.
35. Verification MUST check manifest integrity, dependency closure, selected-workflow consistency, skill names and paths, internal relative references, schema-2 configuration, immutable distribution identity, backend guidance, repository-contained paths, and required agent guidance.
36. Verification MUST distinguish missing, extra, and locally modified distributed files.
37. Locally modified skills MUST be reported without modifying or deleting them.
38. Harness discovery remains an external seam: the skill MUST obtain or request the harness-discovered directories and the command MUST verify exactly that supplied set.
39. A successful verification MUST identify the exact release manifest and installed closure it checked.

### Update planning

40. Before any update plan, the command MUST recover or explicitly fail an earlier interrupted transaction.
41. The command MUST verify the current installation against its installed manifest or, for v0.1.0 bootstrap, the generated legacy baseline.
42. A plan MUST be generated only from a safely extracted and verified target bundle.
43. The immutable plan identity MUST cover at least:
    - operation kind;
    - consumer root;
    - current and target distribution identities;
    - target archive SHA-256;
    - selected workflows and current and target closures;
    - current skill paths and proposed destinations;
    - current file hashes used as apply preconditions;
    - every add, replace, remove, and configuration action;
    - detected local modifications and their approved disposition;
    - schema migration or configuration diff; and
    - relevant changelog information and warnings.
44. Planning MUST NOT write skill, configuration, guidance, backend, or artifact files.
45. The skill MUST present the complete plan and obtain explicit approval before apply.
46. A plan with locally modified skills MUST block apply unless the consumer separately approves discarding those exact modifications. v0.2 MUST NOT merge them.
47. User-selected workflows MUST NOT be removed implicitly. Dependencies no longer required by the target closure MAY be proposed for removal only when unmodified and clearly shown.
48. A schema migration MUST be shown and approved separately from skill replacement.

### Transactional apply and recovery

49. Apply MUST require the exact approved plan identity and MUST reject an altered, incomplete, expired, or already applied plan.
50. Immediately before writes, apply MUST recheck the target archive digest, current installed-file preconditions, configuration preconditions, destinations, and absence of an unrelated active transaction.
51. Apply MUST create durable transaction state inside the consumer repository, stage each replacement on the same filesystem as its destination, and retain backups until final verification succeeds.
52. Transaction state and backups are temporary toolkit-managed recovery data. They MUST be excluded from project artifacts and release integrity and SHOULD be removed after success.
53. Apply MUST replace only distribution-managed skill directories and separately approved configuration fields.
54. Apply MUST NOT modify root agent guidance, `docs/agents/`, backend state, project artifacts, unrelated files, or unapproved local skill changes.
55. Skill replacement MUST complete before distribution identity or installation inventory is updated.
56. After replacement and approved schema/configuration changes, the command MUST run complete consumer verification before committing the transaction.
57. On a caught failure, the command MUST restore every replaced skill directory and previous configuration, verify the restored installation, and report the outcome.
58. If the process is interrupted, the next lifecycle invocation MUST recover the journaled transaction before verification, planning, or another apply.
59. Recovery MUST be idempotent and MUST prefer restoration to attempting an unapproved forward completion.
60. Backups MUST be removed only after target verification and transaction completion are durably recorded.
61. The command MUST support replacing the installed `configure-project` directory that contains the command itself without depending on files after they have been replaced.

### v0.1.0 bootstrap

62. v0.2 releases MUST publish the lifecycle command as a standalone release asset in addition to carrying it in `configure-project`.
63. The distribution MUST generate and test a v0.1.0 baseline manifest from the tagged v0.1.0 source using the v0.2 manifest rules where applicable.
64. Bootstrap MUST require a v0.1.0 consumer root and explicit harness-discovered skill directories because schema 1 has no installation inventory.
65. Bootstrap MUST verify v0.1.0 files against the baseline and surface missing, extra, or modified files before planning.
66. Bootstrap MUST acquire and verify the v0.2 target bundle, calculate the target closure from user-confirmed selected workflows, and use the normal immutable plan and transaction behavior.
67. Migration from schema 1 to schema 2 MUST be a distinct dry-run section and require separate approval.
68. Bootstrap MUST NOT overwrite the installed v0.1.0 `configure-project` merely to gain lifecycle tooling before the approved transaction.
69. Unsupported v0.1 prerelease versions or commit-SHA installations MUST fail with recovery guidance rather than infer a baseline.

## Constraints and decisions

- [ARP-0001](../decisions/ARP-0001-use-a-vendored-consumer-owned-installation-boundary.md) remains the ownership foundation.
- [ARP-0002](../decisions/ARP-0002-use-configure-project-as-the-lifecycle-bootstrap.md) establishes the hybrid bootstrap, manifest, and schema-2 inventory.
- [ARP-0003](../decisions/ARP-0003-apply-workflow-updates-transactionally.md) establishes two-phase transactional replacement and recovery.
- The physical parent of installed skills remains harness-selected and is recorded rather than standardized.
- Third-party installers remain optional initial-copy mechanisms, not lifecycle safety dependencies.
- Consumer-owned files remain outside release integrity and update replacement.
- Git is the supported review and versioning seam.

## Verification

- **Manifest determinism:** Generate twice from the same release tree and compare bytes; reject every omitted, extra, escaping, duplicate, or stale entry.
- **Bundle safety:** Exercise local and HTTPS input; reject archive traversal, links, devices, duplicate members, extra files, digest changes, and manifest mismatches.
- **Fresh-install integration:** Through a real Agent Skills-compatible installer, install `configure-project` and an intentionally incomplete selection at a non-default harness path; calculate closure, install missing skills, verify dry-run destinations, confirm discovery, and leave optional directories absent.
- **Schema-2 validation:** Cover duplicate selection, missing closure members, extra inventory entries, path collisions, escaping paths, wrong directory names, mutable versions, and stale identities.
- **Plan immutability:** Change each covered input after planning and verify apply rejects it without writes.
- **Ownership preservation:** Seed unique bytes in configuration fields not approved for change, guidance, backend state, artifacts, unrelated files, and locally modified skills; verify they survive successful and failed updates.
- **Dependency evolution:** Test added, removed, cyclic, and changed dependencies while preserving selected-workflow intent.
- **Local modifications:** Test block-by-default, explicit discard approval tied to exact hashes, and invalidation when modifications change after approval.
- **Failure injection:** Fail before and after every journal, stage, backup, replace, configuration, verification, and cleanup boundary; verify complete rollback or deterministic next-run recovery.
- **Self replacement:** Update the lifecycle command and `configure-project` that are executing the transaction.
- **v0.1.0 bootstrap:** Smoke-install the tagged release through a real installer, test clean migration, modified-file blocking, separate schema approval, and target verification.
- **Harness independence:** Verify one shared skill root, several roots, and explicit discovered-directory input without assuming `.agents/skills/`.
- **Regression:** Existing source, dependency, configuration, consumer, fixture, and documentation verification continues to pass.

## Out of scope

- Multiple or nested workflow configurations in one Git repository.
- Automatic conflict merging.
- Automatic application-artifact or configuration migration without separate approval.
- A required third-party installer or hosting-provider API.
- One mandated skill parent directory.
- Global mutable installations.
- Updating consumer application code or project artifacts.
- Cryptographic release signing or new trust infrastructure.
- Support for bootstrapping arbitrary v0.1 prerelease or commit-SHA installations.

## Open items

- Choose the implementation language and packaging that satisfy the portable standalone-command requirement.
- Choose stable command names and machine-readable output encoding.
- Choose the exact release-archive format and canonical asset names.
- Choose the repository-contained transaction-state location and cleanup policy.

These are implementation choices that must satisfy the behavior above; none changes the accepted lifecycle or ownership boundary.
