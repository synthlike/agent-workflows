# v0.2 fresh-project lifecycle

## Problem

Fresh consumers must currently calculate workflow dependencies manually and use an Agent Workflows source checkout to verify installation. That makes initial adoption error-prone even though the project already defines a stable vendored ownership boundary. There is only one v0.1.0 installation, so a public migration and transactional updater would add substantial complexity without serving an installed population.

## Desired behavior

A user can start with a fresh Git repository, install `configure-project` and any desired workflows through an Agent Skills-compatible installer, and invoke `configure-project`. Installed lifecycle assets calculate the selected workflows' closure, obtain missing skills from a verified current-release bundle, propose every repository-contained destination, and write only after approval. Configuration completes after the harness confirms discovery of the complete closure and installed verification passes.

The configured project records schema-2 installation intent and paths and can verify itself without an Agent Workflows source checkout. Existing project guidance, conventions, backend state, and artifacts remain consumer-owned. v0.2 does not automate cross-version updates; the sole v0.1.0 installation migrates through reviewed repository-local work, and reusable update behavior is deferred to v0.3.

## Requirements

### Lifecycle assets and release metadata

1. Every valid v0.2 installation MUST include an intact `configure-project` skill.
2. `configure-project` MUST be the human-facing entrypoint for fresh configuration and installed verification.
3. Its skill directory MUST carry a deterministic lifecycle command and the current machine-readable release manifest through relative paths.
4. The command MUST expose deterministic non-interactive operations for manifest validation, dependency closure, release-bundle verification, installation inspection, and consumer verification.
5. Human intent, dry-run review, approval, and harness discovery confirmation MUST remain responsibilities of the skill workflow.
6. Each v0.2 release MUST publish one deterministically generated machine-readable manifest.
7. The manifest MUST identify its format version, distribution source and exact release version, supported consumer-configuration schema versions, and every distributed skill with its direct dependencies.
8. The manifest MUST list every distributed file inside each skill directory except the manifest itself, keyed by skill-relative path with SHA-256.
9. Manifest integrity MUST exclude installer-owned locks or external symlinks, caches, OS metadata, consumer configuration and guidance, backend state, and project artifacts.
10. Manifest generation MUST fail for unknown or missing skills, stale dependency declarations, missing or extra distributed files, duplicate paths, or paths escaping their skill directory.
11. The release MUST provide one self-contained immutable archive containing the manifest, complete skill directories, lifecycle assets, and relevant changelog information.
12. The command MUST accept the current release archive by local path or HTTPS URL without requiring a hosting-provider API.
13. It MUST compute SHA-256 over the complete archive and safely extract only the expected layout.
14. Extraction MUST reject absolute paths, parent traversal, duplicate members, links, device files, missing manifest content, extra skill content, and file-digest mismatches.
15. Cryptographic signing or new trust infrastructure is not required for v0.2.

### Configuration schema 2

16. A configured v0.2 consumer MUST use `schema_version: 2` in its single root `.agents/workflows.yaml`.
17. Schema 2 MUST retain distribution identity, issue-backend settings, artifact capabilities, and paths from schema 1.
18. Schema 2 MUST add an installation inventory containing:
    - the unique workflows explicitly selected by the user; and
    - a unique mapping from every installed skill in their closure to its harness-discovered, repository-relative directory.
19. Every selected and installed skill MUST exist in the release manifest.
20. Every inventory path MUST remain within the consumer root, be unique, name a directory matching the skill, and resolve to the manifest-verified skill contents.
21. The installed set MUST equal or contain the complete transitive closure of selected workflows and MUST include `configure-project`.
22. Incidental transitive dependencies MUST NOT silently become user-selected intent.
23. Installer-owned lock files MAY be inspected as evidence but MUST NOT become canonical Agent Workflows lifecycle state.
24. Distribution identity and inventory MUST be shown in the dry run and written only after approval.

### Fresh-project configuration

25. A fresh installation MAY initially contain only `configure-project` and some selected workflows.
26. `configure-project` MUST ask for user-selected workflows only when intent is not already explicit; it MUST calculate dependencies rather than ask the user to do so.
27. The command MUST compare harness-discovered skills with the current manifest and calculated closure and report missing, unexpected, duplicate, incomplete, or modified skills.
28. Existing incomplete or modified skill directories MUST block automated writes and receive manual recovery guidance; fresh configuration MUST never replace them.
29. When dependencies are missing, the skill MUST obtain the verified current release archive and generate a dry run that shows archive identity, selected workflows, closure, every source skill, every destination, and configuration changes.
30. The parent of the discovered `configure-project` directory MUST be the default destination for each missing skill.
31. The user MUST be able to override each destination with another repository-contained path.
32. Apply MUST revalidate the archive, current installation, absent destinations, and approved dry-run identity immediately before writes.
33. Apply MAY create only previously absent skill directories and the separately approved configuration and guidance files. It MUST NOT replace, remove, or update existing skill directories.
34. Each new skill directory MUST be staged completely before becoming visible at its destination.
35. On failure, the command MUST stop, identify any newly created directories, and provide cleanup guidance. General transaction journals and automatic rollback are not required.
36. Optional artifact and local-issue directories MUST remain absent until their first content is written.
37. Configuration MUST NOT complete until the consumer's harness confirms discovery of every skill in the closure.
38. Complete installed verification MUST pass before the skill reports success.
39. The user SHOULD commit the reviewed installation, configuration, and guidance before creating project artifacts.

### Installed verification

40. Consumer verification MUST run entirely from lifecycle assets installed with `configure-project`, without a distribution checkout.
41. Verification MUST accept the consumer root and exact harness-discovered skill directories without assuming a physical parent such as `.agents/skills/`.
42. Verification MUST check manifest identity, selected-workflow closure, inventory consistency, skill directory names, all distributed file hashes, internal relative references, and repository-contained paths.
43. Verification MUST validate schema 2, immutable distribution identity, issue-backend guidance, artifact settings, and root agent guidance.
44. Verification MUST distinguish missing, extra, and modified distributed files and MUST never alter them.
45. Disabled capabilities MUST require no artifact directory, and optional directories MUST remain lazy.
46. Successful machine-readable and human-readable output MUST identify the exact release and installed closure verified.

### Existing v0.1.0 installation and updates

47. The known v0.1.0 installation MUST migrate through reviewed repository-local implementation work, not a public automated bootstrap interface.
48. That migration MUST preserve the v0.1 ownership boundary, show the schema-2 configuration diff, run full v0.2 verification, and be committed normally.
49. v0.2 MUST NOT publish a legacy baseline manifest, standalone migration asset, automated schema migration, reusable update planner, file replacement engine, transaction journal, rollback system, interruption recovery, or self-update behavior.
50. v0.2 documentation MUST state that cross-version updates remain reviewed manual operations and that reusable safe updates are deferred to v0.3.
51. A manual update MUST continue to surface local modifications, preserve consumer-owned files, review the diff, update distribution identity only after accepting installed source, and run complete verification.

## Constraints and decisions

- [ARP-0001](../decisions/ARP-0001-use-a-vendored-consumer-owned-installation-boundary.md) remains the ownership foundation.
- [ARP-0002](../decisions/ARP-0002-use-configure-project-as-the-lifecycle-bootstrap.md), as refined by ARP-0004, establishes the mandatory bootstrap, manifest, schema-2 inventory, and fresh closure behavior.
- [ARP-0004](../decisions/ARP-0004-ship-v0.2-for-fresh-project-adoption.md) limits v0.2 to fresh-project adoption and supersedes transactional updates as v0.2 scope.
- Skills remain repository-vendored, harness-discoverable, and independent of one parent directory.
- Git remains the supported review and recovery seam.
- Third-party installer commands remain illustrative initial-copy mechanisms rather than guaranteed lifecycle APIs.

## Verification

- **Manifest determinism:** Generate twice from the same source tree and compare bytes; reject unknown, missing, stale, duplicate, escaping, extra, and mismatched entries.
- **Archive safety:** Exercise local and HTTPS input and reject traversal, links, devices, duplicates, unexpected content, changed bytes, and digest mismatches.
- **Closure behavior:** Cover no dependencies, transitive dependencies, cycles, unknown selections, missing skills, and selected-versus-incidental intent.
- **Schema-2 validation:** Cover duplicate selection, stale inventory, path collisions, escaping paths, incorrect directory names, mutable versions, and incomplete closure.
- **Fresh empty project:** Install an intentionally incomplete selection through the currently used Agent Skills-compatible installer, calculate closure, show destinations, add only missing directories, confirm harness discovery, verify, and leave optional directories absent.
- **Fresh existing project:** Preserve surrounding agent guidance, existing artifact conventions, backend state, and project files while adding only approved setup.
- **Destination behavior:** Cover the `configure-project` sibling default, explicit overrides, several skill roots, occupied destinations, and paths outside the repository.
- **Apply preconditions:** Change the archive, discovered skills, destination contents, or dry-run inputs after approval and verify writes are rejected.
- **Failure behavior:** Inject failure before staging and before each destination publication; verify no existing skill or consumer-owned file changes and cleanup guidance identifies new content.
- **Installed verification:** Run from copied `configure-project` lifecycle assets with no source checkout and detect missing, extra, and modified files.
- **Known migration:** Apply the reviewed v0.1.0-to-v0.2 repository migration and verify schema 2 and full installed integrity.
- **Regression:** Existing skill, backend, dependency, configuration, consumer, fixture, and documentation verification continues to pass.

## Out of scope

- Public or automated v0.1.0 migration.
- Reusable cross-version update planning or replacement.
- Transaction journals, backups, rollback, interruption recovery, or self-update.
- Automatic conflict merging, schema migration, or artifact migration.
- Multiple or nested workflow configurations in one Git repository.
- A required installer, hosting-provider API, or fixed skill parent directory.
- A broad cross-harness compatibility matrix.
- Cryptographic release signing or new trust infrastructure.

## Open items

- Choose the lifecycle command implementation language and packaging.
- Choose the exact manifest schema, command names, output encoding, archive format, and release asset names.
- Define the current harness's discovery-confirmation seam for integration testing.

These implementation choices must satisfy the observable behavior above; none changes the accepted fresh-project boundary.
