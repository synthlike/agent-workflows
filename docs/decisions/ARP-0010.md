# Migrate one semantic record route through a resumable staged move

## Context

ARP-0009 makes semantic record authority independent of storage backend but intentionally leaves route-change migration unsupported. A project now needs to move complete routes among local Markdown, GitHub, and Bear without changing semantic type or silently losing history. Cross-provider writes, route configuration, and source retirement cannot form one atomic transaction. Provider-native issue identifiers and metadata also cannot always be reproduced exactly.

## Decision

Agent Workflows will provide a manually invoked `migrate-records` workflow for one complete semantic route at a time.

A migration includes active and retained historical records and is permitted only when adapter-owned migration capabilities can export and import every portable value with semantic losslessness. Record type and exact content bytes remain unchanged. Free-form links are not rewritten. Non-issue semantic IDs remain stable; provider-assigned issue IDs may change only with durable source-to-destination mapping and canonical provenance. Structured relationships and managed references are recreated through destination operations.

The workflow uses a project-contained resumable journal and three separately approved stages:

1. create and verify destination records while the source route remains authoritative;
2. cut over the route through `configure-workflows` deterministic plan/apply; and
3. retire source records after verified cutover.

A cooperative source write freeze and complete revision recheck guard cutover. Before cutover, abandoned staged records require separately approved cleanup. After cutover, recovery always rolls forward because the destination may already contain new authoritative writes. Non-issue sources archive; active source issues cancel with a migration tombstone and destination reference; terminal issues retain status and receive provenance.

The skill is distributed with `disable-model-invocation: true`. Natural-language migration requests direct the user to invoke `/skill:migrate-records`; invocation alone authorizes no inspection or mutation beyond the workflow's explicit boundaries.

## Rationale

Strict one-route plans keep authority and recovery bounded. Capability-gated semantic preservation avoids both provider coupling and silent lossy conversion. A journaled saga is honest about the lack of distributed transactions, while deterministic configuration apply prevents migration from introducing a second route-editing mechanism. Manual invocation protects sensitive inventory and provider inspection from accidental activation.

## Consequences

- Local Markdown and GitHub need migration support for issues and non-issue records; Bear needs it for its eleven non-issue types.
- Normal list/search contracts remain unchanged; migration-specific export must enumerate retained history.
- Providers may use canonical provenance when native timestamps, authors, assignees, or identifiers cannot be reproduced exactly.
- Planning must fail before writes when any source value, relationship, collision, revision, identity, or destination capability is unresolved.
- Migration is not atomic. Journals, idempotence, resume, stage-specific approval, and roll-forward recovery are required.
- Source records and Bear notes are retained rather than deleted.
- Semantic reclassification, heuristic content-link rewriting, Things support, and implicit configuration-time migration remain out of scope.
