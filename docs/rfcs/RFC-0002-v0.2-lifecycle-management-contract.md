# v0.2 lifecycle-management contract

## Summary

Decide how v0.2 should make the complete consumer lifecycle—install, configure, verify, and update—self-contained and safe without weakening the harness-independent ownership boundary accepted for v0.1.

The confirmed v0.2 destination is:

> A consumer can manage Agent Workflows without checking out the source repository, manually calculating dependencies, or risking consumer-owned files.

The material decision is which interface and release metadata own that lifecycle behavior.

## Motivation

v0.1 established a reproducible contract and verification model, but leaves several operations manual or dependent on a source checkout:

- consumers or installers calculate dependency closure from a Markdown table;
- consumer verification runs from `scripts/` in the Agent Workflows distribution;
- no machine-readable release manifest binds version, dependency graph, configuration schema, and distributed files;
- updates are a documented reviewed procedure rather than an executable workflow;
- configuration may need a human to identify source and version when installation metadata is unavailable; and
- local modifications can be detected when canonical source is available, but there is no self-contained update comparison or replacement operation.

These gaps make the v0.1 safety contract possible to follow but unnecessarily difficult to execute consistently.

## Requirements and constraints

### Requirements

- Preserve the vendored, consumer-owned boundary established by [ARP-0001](../decisions/ARP-0001-use-a-vendored-consumer-owned-installation-boundary.md).
- Keep `configure-project` mandatory and make it the v0.2 lifecycle entrypoint.
- Carry the deterministic lifecycle command and current release manifest inside the intact `configure-project` directory so every valid installation has them.
- Make consumer verification available without a separate source-repository checkout.
- Publish machine-readable release identity, configuration-schema compatibility, direct skill dependencies, and SHA-256 integrity data for every distributed file inside each skill directory except the manifest itself.
- Exclude installer-owned files outside skill directories, consumer-owned files, symlinks outside skill directories, caches, and OS metadata from manifest integrity.
- Calculate dependency closure for a selected workflow set and detect incomplete installations.
- During fresh configuration, acquire the current release bundle and propose missing dependencies beside the already discovered `configure-project` directory by default, with explicit per-skill destination overrides.
- Show every proposed destination in the dry run and complete configuration only after the consumer's harness confirms discovery of the resulting closure.
- Detect locally added, removed, or modified distribution-managed files before update replacement.
- Compare the installed and target releases and present relevant changelog information.
- Recheck installed-file and target-bundle hashes immediately before apply.
- Journal each update, keep backups until success, automatically restore all distribution-managed skill directories on failure, and recover an interrupted transaction before another lifecycle operation.
- Update consumer configuration only after skill replacement succeeds; restore the previous configuration if finalization fails.
- Preserve `.agents/workflows.yaml`, agent guidance, `docs/agents/`, backend state, project artifacts, and explicit local skill modifications unless the consumer separately approves a change.
- Require an explicit dry run and approval before an update writes files.
- Use a two-phase command: stage and verify a self-contained target bundle supplied by local path or HTTPS URL, emit an immutable update plan, then apply exactly that approved plan without invoking a third-party installer.
- Bind the approved plan to the SHA-256 of the complete staged bundle and recheck it before apply; cryptographic signing is out of v0.2 scope.
- Update recorded distribution identity only after the corresponding installed source is accepted.
- Publish the lifecycle command as a standalone v0.2 release asset for the one-time bootstrap from v0.1.0.
- Ship a generated v0.1.0 baseline manifest so bootstrap can verify existing files, surface modifications, and produce the normal two-phase update plan.
- Test fresh v0.2 installation and update from v0.1.0 through a real Agent Skills-compatible installer.
- Keep interfaces behavioral and portable across agent harnesses.

### Constraints

- Third-party Agent Skills installers do not implement an Agent Workflows-specific dependency or update contract.
- Installed skills may live under different harness-selected parent directories.
- A selective installation cannot assume all distribution scripts and documentation are present.
- Skills are Markdown workflows executed by an agent; deterministic file integrity and replacement behavior is safer in a small executable tool than in unconstrained prose.
- v0.1 configuration uses `schema_version: 1` and one `.agents/workflows.yaml` per Git root.
- v0.2 uses `schema_version: 2` and adds a reviewed installation inventory containing user-selected workflows and their harness-discovered skill paths.
- The v0.1 bootstrap may propose the schema-2 migration but writes it only after separate approval; migration is never an implicit update side effect.
- Existing v0.1 consumers have no machine-readable manifest in their repositories beyond configuration and any installer-owned lock data.
- The toolkit must remain independent of a particular application, programming language, issue tracker, documentation generator, or agent harness.

### Assumptions

- v0.2 may add a small portable executable surface while retaining skills as the human-facing workflow layer.
- Release artifacts can include generated metadata derived from authoritative source files.
- Git remains the supported v0.2 review and versioning seam.
- A v0.1.0 installation can be identified from `.agents/workflows.yaml` and inspected skill directories even without a v0.2 manifest.

### Preferences

- Prefer one manifest over duplicated dependency, version, and integrity metadata.
- Prefer deterministic commands for inspection, closure calculation, comparison, and file replacement.
- Prefer skills for clarification, dry-run presentation, approval, and routing.
- Prefer extending the v0.1 verifier over creating parallel validation logic.
- Prefer explicit failure with recovery instructions over best-effort mutation.

## Non-goals

- Multiple or nested workflow configurations in one Git repository.
- Automatic conflict merging.
- Automatic configuration or artifact migration.
- Coupling to one agent harness or physical skill parent directory.
- Requiring one third-party installer.
- Globally shared mutable installations.
- Updating application code or project artifacts.
- Silent replacement of locally modified skills.
- Cryptographic release signing or a new trust infrastructure.

## Open questions

None.

## Options

### Option A: Hybrid skill and deterministic lifecycle command

Ship a harness-discoverable lifecycle skill backed by a small portable command. The skill owns intent clarification, dry-run review, approval, and recovery guidance. The command owns manifest parsing, dependency closure, integrity comparison, verification, and approved file replacement.

Advantages:

- separates human decisions from deterministic mutation;
- can be tested without an agent harness;
- provides a self-contained consumer interface;
- reuses the existing verifier; and
- remains independent of third-party installer behavior.

Disadvantages:

- introduces an executable distribution surface and packaging questions;
- the command must be available in selective installations; and
- responsibilities between skill and command must be explicit.

### Option B: Skill-only lifecycle management

Add lifecycle skills that inspect files, calculate closure, present diffs, and perform updates using ordinary agent tools.

Advantages:

- stays within the existing Agent Skills distribution model;
- requires no separate executable packaging; and
- can adapt explanations and recovery to project context.

Disadvantages:

- deterministic integrity and replacement behavior is harder to guarantee;
- behavior may vary by harness or model;
- testing mutation safety is less direct; and
- duplicates logic already implemented in Python verification scripts.

### Option C: Standalone lifecycle CLI

Provide a command that installs, configures, verifies, and updates without a skill-mediated workflow.

Advantages:

- deterministic and straightforward to automate;
- supports strong integration testing; and
- offers one concrete lifecycle interface.

Disadvantages:

- risks becoming an installer coupled to filesystem and harness conventions;
- configuration still needs human decisions and adoption-aware review;
- broadens the project beyond semantic agent workflows; and
- may duplicate third-party installer functionality.

### Option D: Installer-specific integration

Build around one third-party Agent Skills installer and its lock format, commands, and destination behavior.

Advantages:

- leverages an existing installation user experience;
- may reuse installer discovery and update operations; and
- minimizes custom command surface.

Disadvantages:

- weakens harness and installer independence;
- depends on an external interface and metadata contract;
- may not preserve the v0.1 ownership boundary; and
- excludes manual and alternative installations.

### Option E: Keep the v0.1 manual lifecycle

Continue publishing Markdown dependencies, source-checkout verification, and reviewed update instructions.

Advantages:

- adds no executable or packaging complexity;
- preserves maximum flexibility; and
- requires no compatibility work.

Disadvantages:

- does not achieve the confirmed v0.2 destination;
- leaves closure and update execution manual;
- keeps verification dependent on distribution source; and
- provides little value over v0.1.0.

## Recommendation

Choose Option A: a hybrid skill and deterministic lifecycle command. `configure-project` remains mandatory, becomes the lifecycle skill, and carries the command plus current release manifest inside its own directory.

This preserves Agent Workflows as a semantic workflow kit while moving integrity-sensitive operations behind a testable seam. The skill can require dry-run approval and explain conflicts; the command can consume one generated manifest, calculate closure, verify installed files, and execute only an already-approved replacement plan. Bundling the deterministic assets with the already mandatory skill avoids requiring dependency resolution to install the dependency resolver.

The command stages and verifies the target release, produces a deterministic plan for review, and applies that exact approved plan itself. It does not delegate update safety to a third-party installer.

Manifest integrity covers every distributed file inside each skill directory, keyed by skill-relative path with SHA-256. It excludes only the manifest itself and files outside distribution-managed skill directories, including installer locks and symlinks, caches, OS metadata, configuration, guidance, backend state, and project artifacts.

For v0.1.0 compatibility, v0.2 publishes the same lifecycle command as a standalone release asset and ships a generated v0.1.0 baseline manifest. The bootstrap verifies existing v0.1.0 files, surfaces modifications, and produces the normal two-phase plan without first overwriting the installed `configure-project`.

v0.2 uses configuration schema 2 with an installation inventory containing the user-selected workflows and discovered skill paths. The v0.1 bootstrap proposes this as a separate reviewed migration and writes it only after approval; no second lock file is introduced.

The canonical target is a self-contained release bundle supplied by local path or HTTPS URL. It contains the target manifest and complete skill files. The command stages it locally, verifies file integrity, and binds the approved plan to the complete bundle's SHA-256. It does not require GitHub APIs or installer behavior; cryptographic signing remains out of v0.2 scope.

Updates are transactional across the distribution-managed skill set. The command journals the operation, stages replacements beside each destination, rechecks current and target hashes, retains backups until success, and updates configuration last. A caught failure restores the previous installation; the next invocation recovers an interrupted transaction before doing other work. Consumer artifacts are never part of the transaction.

## Resolution

Accepted by the decision owner on 2026-08-24. v0.2 adopts Option A: `configure-project` becomes the hybrid lifecycle entrypoint, carrying a deterministic command and machine-readable manifest. Updates use verified self-contained bundles, schema-2 installation inventory, explicit two-phase approval, and transactional replacement with recovery. A standalone copy of the command and a v0.1.0 baseline manifest provide the one-time bootstrap path. Fresh configuration resolves missing dependencies from the current bundle, proposes destinations beside `configure-project` by default, allows path overrides, and requires post-install harness discovery confirmation.

Consequential decisions were recorded in [ARP-0002](../decisions/ARP-0002-use-configure-project-as-the-lifecycle-bootstrap.md) and [ARP-0003](../decisions/ARP-0003-apply-workflow-updates-transactionally.md). The later [fresh-project scope amendment](RFC-0003-reduce-v0.2-to-fresh-project-lifecycle.md) and [ARP-0004](../decisions/ARP-0004-ship-v0.2-for-fresh-project-adoption.md) defer reusable updates to v0.3. The original full-lifecycle specification is retained as superseded design history; current v0.2 behavior is defined separately.
