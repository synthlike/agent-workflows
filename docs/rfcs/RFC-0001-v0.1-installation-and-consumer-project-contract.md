# v0.1 installation and consumer-project contract

## Summary

Define the supported v0.1 boundary between the Agent Workflows distribution, an installation mechanism, and a consumer repository.

The proposed contract is a behavior-based, harness-independent model:

1. Vendor a dependency-closed selection of skill directories into the consumer repository using an Agent Skills-compatible installer or a manual equivalent.
2. Preserve every installed skill directory intact and place it where the consumer's agent can discover it.
3. Run the installed `configure-workflows` skill from the Git repository root before using any other installed workflow.
4. Review and approve its dry run, then commit the resulting consumer configuration and guidance.
5. Treat later distribution updates as reviewed replacements of reusable toolkit files, never as implicit migrations of consumer-owned files or artifacts.

A third-party installation command may be documented as an example, but is not part of the guaranteed v0.1 interface.

## Motivation

Current documentation describes installation, configuration, ownership, and updates across several pages, but does not provide one precise compatibility boundary. In particular, it does not settle:

- what an installer must preserve;
- whether workflow dependencies must also be installed;
- whether configuration is optional;
- which files belong to the distribution versus the consumer project;
- how an installation records its source version;
- whether a physical skill path or third-party CLI is guaranteed;
- what updates may overwrite; or
- how configuration behaves in monorepos or nested directories.

Without an explicit contract, two installations can appear successful while exposing different workflow capabilities or risking consumer-owned content during an update.

## Requirements and constraints

### Requirements

#### Installation unit

- v0.1 skills are vendored and versioned with the consumer repository; they are not runtime services or globally shared mutable state.
- An installation MUST include `configure-workflows`.
- An installation MAY select only some workflows, but the selected set MUST include every transitively referenced workflow.
- The repository MUST publish a dependency table for the release. Until a supported installer consumes dependency metadata, the installer or user is responsible for selecting the documented closure.
- Each installed skill directory MUST be copied intact, including `SKILL.md` and all files needed through relative references.
- Installed skills MUST be discoverable by the consumer's Agent Skills-compatible agent.
- The physical parent directory of installed skills is deliberately unspecified. `.agents/skills/` is one supported example, not a mandated location.
- Manual copying is a supported fallback when it produces the same intact, dependency-closed result.
- Commands for third-party installers, including `npx skills@latest add ...`, are illustrative and not stable v0.1 APIs.

#### Consumer root and configuration

- One Git repository root is one v0.1 consumer-project root.
- A consumer project MUST have exactly one `.agents/workflows.yaml`, at that root.
- Nested workflow configurations, configuration inheritance, and multiple independently configured roots inside one Git repository are unsupported.
- Monorepos MAY choose artifact paths suitable for their layout within the single root configuration.
- `configure-workflows` MUST be run from the consumer root before another installed workflow is used.
- `configure-workflows` MUST inspect existing conventions, present a complete dry run, and obtain explicit approval before writing.
- `.agents/workflows.yaml` is the canonical workflow configuration.
- Its configured paths MUST be relative to the consumer root and MUST remain within it.
- The configuration MUST record `distribution.source` and `distribution.version`.
- `distribution.version` MUST be an exact release identifier. A local or prerelease installation MAY use an immutable commit SHA instead.
- Configuration and generated agent guidance SHOULD be committed before project artifacts are created.
- Optional artifact directories MUST be created lazily, when their first artifact is written.

#### Consumer-facing operational contract

After configuration:

- workflows MUST resolve artifact locations and optional capabilities through root `.agents/workflows.yaml`, rather than toolkit defaults or hardcoded consumer paths;
- issue operations MUST follow the configured `docs/agents/issue-tracker.md` adapter;
- concise root agent guidance MUST point agents to `.agents/workflows.yaml` and `docs/agents/` rather than duplicating their details;
- disabled optional capabilities MUST remain disabled unless the user explicitly approves enabling them; and
- installation or configuration MUST NOT migrate existing artifacts as a side effect.

#### Ownership boundary

Distribution-managed reusable files are:

- the installed, vendored skill directories and their internal references.

Consumer-owned files are:

- `.agents/workflows.yaml`;
- root agent guidance, including any inserted workflow pointer;
- generated or adapted guidance under `docs/agents/`;
- issue-backend state;
- all RFCs, ARPs, specifications, domain documents, meeting notes, issues, research, prototypes, and other project artifacts; and
- any explicit local modifications to vendored skills.

Project policy overrides toolkit defaults. Consumers SHOULD customize configuration and project guidance instead of vendored skill files when the workflow itself does not need to change.

#### Updates

- v0.1 provides no automatic updater or migration system.
- A consumer MAY update through the same installer or manual process used for installation, but MUST review the resulting diff before committing it.
- An update MAY replace unmodified distribution-managed files.
- An update MUST preserve consumer-owned configuration, guidance, backend state, and project artifacts.
- An update MUST detect or visibly surface locally modified vendored files rather than silently overwrite them.
- An update MUST NOT automatically migrate configuration schemas or project artifacts.
- The consumer MUST update `distribution.source` or `distribution.version` only after accepting the corresponding installed source.
- Structural verification appropriate to the installed release MUST pass after an update.

### Constraints

- The kit must remain independent of a particular agent harness, application, programming language, issue tracker, or documentation generator.
- Generic Agent Skills installers may not understand toolkit-specific dependency metadata.
- The repository currently has no automated updater, package manifest, release tag, or machine-readable dependency mechanism.
- Existing configuration and setup guidance already establish `.agents/workflows.yaml`, `docs/agents/`, lazy artifact directories, and dry-run approval as conventions.

### Assumptions

- The consumer project uses Git or provides equivalent review and versioning semantics; Git is the supported v0.1 case.
- The agent harness can discover vendored Agent Skills and resolve files referenced relative to each skill directory.
- A human can review installation and configuration diffs.
- Release documentation can provide an accurate dependency table even when dependency selection is manual.

### Preferences

- Prefer an Agent Skills-compatible installer over manual copying for convenience.
- Prefer release tags over commit SHAs for stable releases.
- Prefer existing consumer conventions over introducing parallel artifact layouts.
- Prefer adopting existing artifacts in place over migrating or renaming them.

## Non-goals

- Standardizing one physical skill installation directory.
- Guaranteeing the syntax, availability, or behavior of a third-party installer CLI.
- Defining a global installation shared by multiple repositories.
- Supporting multiple or nested workflow configurations in one Git repository.
- Providing automatic dependency resolution, update merging, rollback, or schema migration.
- Migrating existing project artifacts during installation or configuration.
- Preventing consumers from modifying vendored skills.
- Defining the detailed artifact semantics already owned by individual workflows and backend contracts.

## Open questions

None. Consumer checks are implemented by [consumer installation verification](../verifying-installation.md), and the first release identifier is `v0.1.0`.

## Options

### Option A: Behavior-based vendored contract with dependency closure

Vendor an intact, dependency-closed skill selection at any harness-supported path, require root configuration, distinguish distribution-managed from consumer-owned files, and make every update a reviewed operation.

Advantages:

- remains harness- and installer-independent;
- permits both full and selective installation;
- makes ownership and update safety explicit;
- matches the repository's existing direction; and
- supports reproducible diagnosis through source-version recording.

Disadvantages:

- dependency selection is partly manual in v0.1;
- compatibility cannot be inferred from one standardized filesystem path; and
- conforming installers need behavioral validation rather than a package-format check alone.

### Option B: Fixed-path, full-suite installation

Require every skill under a single path such as `.agents/skills/`, with no selective installation.

Advantages:

- simple dependency and completeness rules;
- straightforward structural validation; and
- fewer installation variants.

Disadvantages:

- couples the kit to a filesystem convention not shared by every harness;
- installs workflows consumers may not want; and
- conflicts with the goal of remaining agent-harness independent.

### Option C: Installer-specific package contract

Choose one third-party installer and define its command, selection behavior, destination, and update semantics as the v0.1 interface.

Advantages:

- provides a concrete happy path;
- can offer a familiar command and user experience; and
- delegates some packaging behavior.

Disadvantages:

- makes the contract depend on behavior outside this repository;
- may change independently of this project's releases; and
- excludes compatible manual and alternative installations.

### Option D: Keep current guidance without a normative contract

Continue documenting installation and updates as recommendations spread across existing pages.

Advantages:

- requires no release-contract work; and
- preserves maximum implementation flexibility.

Disadvantages:

- leaves dependency completeness, ownership, configuration, and update safety ambiguous;
- makes compatibility claims difficult to test; and
- risks silent divergence between consumer projects.

## Recommendation

Accept Option A.

It gives v0.1 a precise minimum contract without promising an installer, updater, or configuration model that does not exist. It also preserves selective installation while requiring dependency completeness, and it clearly protects consumer-owned files and artifacts from installation and update operations.

Before release, implementation work should publish the v0.1 dependency table, align installation and update documentation with this contract, ensure configuration always records immutable source-version information, and add consumer-oriented structural verification.

## Resolution

Accepted by the decision owner on 2026-08-24. v0.1 adopts Option A: a behavior-based, dependency-closed vendored installation; required root configuration; an explicit distribution-versus-consumer ownership boundary; and reviewed, non-migrating updates.
